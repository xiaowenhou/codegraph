结论先行

codegraph 的价值取决于问题对「跨文件结构追踪」的依赖度:依赖度高(业务调用链) → 明显更快更省;依赖度中(数据链路)→ 微赢;依赖度低(框架内部机制)→ 平手甚至更慢。 你接手项目时的问法——"前端调哪个接口、查哪张表、谁写入、怎么异步"——恰好是依赖度最高的那一类,所以对本项目 value 是真实的。 跨会话场景优势显著:WITHOUT 的知识存在 agent 上下文里、换会话即蒸发;codegraph 的索引持久在磁盘,换会话 1~4 次调用即复得。

M 方法学 — 怎么跑的

  • 工具:项目自带 scripts/agent-eval/run-all.sh —— with 臂 = codegraph-only MCP(Read/Grep/Bash 仍可用),without 臂 = 空 MCP。两臂唯一差异就是 codegraph 是否存在。
  • 防作弊(no-cli-shim):两臂都屏蔽 codegraph CLI(净化 PATH + PreToolUse 钩子双保险),防止 without 臂通过 Bash 偷调 CLI。历史统计中 14/15 的 without 臂会这么干,必须拦。
  • 模型:统一 sonnet / effort=high —— 项目强制的地板模型策略(在"较笨"模型上验证,优势能泛化到更强的 agent)。
  • 问题形态:多轮问题用 || 分隔,自动 --resume 续上下文,模拟真实多轮追问。
  • 污染检查:每一臂结束后核对 CLI calls that RETURNED output = 0 —— 三轮全部通过。
⚠ 样本量局限 每轮 n=1。项目文档明确 "run-to-run variance is large — never conclude from n=1"。数字看方向和量级,单次绝对值会波动。

一个精确的边界

codegraph 的会话内去重(explore-session-state.ts)是 per-session、不跨会话的——换新会话后 explore 会重新返回全部源码(这是设计意图:新 agent 从没看过,必须重新给)。

所以准确的说法是:「检索能力(索引)跨会话持久,重新取回只需 1~4 次调用」,而不是「explore 的结果本身直接继承」。但这一点对 WITHOUT 仍是压倒性优势——它没有持久底座,每次都是从头挖。

净结论WITHOUT 把知识当会话态(上下文),WITH 把知识当持久态(磁盘索引)。换会话的痛点对 codegraph 不构成伤害,因为它的资产根本不放在上下文里。

05 综合结论 — 赢面光谱

三轮合起来的规律,比任何单轮都可靠:

依赖度低 框架内部机制推理
→ 平手甚至输
依赖度中 单条数据链路
→ 微赢(工具/成本省)
依赖度高 多事件异步调用链
→ 明显赢(快/省/0 Read)

对 PEMS 的落点:接手维护时的典型问法——"前端调哪个接口、查哪张表、谁写入、怎么异步、有无缓存"——全部落在光谱右端。这类问题 With 臂的省幅:工具调用 -51%~-54%、token -30%~-39%、cost -11%~-28%,且越复杂的链路优势越明显。

06 现场验证计划 — 在 PEMS 上持续积累

本报告是受控 A/B 的起点。接下来在真实使用中积累体验,记录点:

  • 工具采纳:实际会话里 agent 是否稳定先调 codegraph_explore 而非直接 Read。
  • sufficiency:explore 一次返回是否足够让 agent 停下,还是常需第二次/转 Bash。
  • 跨会话:连续多个会话中,第二次起的会话是否明显更快(索引热复用)。
  • 盲区:哪些问题 codegraph 答不上导致 agent 退回 Read —— 记录下来作为后续定制方向(如异常分发链、事务切面)。
  • 框架机制题:遇到"这个框架内部怎么运行"时,确认它会比纯业务题慢 —— 这类题直接让 agent 查源码反而更快。
方法提醒若要做严肃回归对比,遵循项目方法论:同模型(sonnet/high)、≥2 次取中位数、跑前预热 daemon、防 CLI 污染。单次结论只信方向不信绝对值。
